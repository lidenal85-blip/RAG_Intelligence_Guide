1.3 Когда RAG нужен, а когда нет

RAG — мощный паттерн, но не серебряная пуля. Нужно понимать границы его применимости и альтернативы.

✅ КОГДА RAG НУЖЕН

  • 📚 Динамические знания — документы часто обновляются (база знаний, поддержка клиентов).
  • 🔍 Прозрачность источников — нужны ссылки на источник ответа (юристы, врачи, инженеры).
  • 💰 Большие объёмы данных — миллионы документов; fine‑tune модели физически невозможен.
  • 🌍 Мультипредметность — вопросы из разных областей, которые LLM не покрывает.
  • ⚡ Быстрый старт — не нужно собирать датасет для обучения, достаточно загрузить документы.

❌ КОГДА RAG НЕ НУЖЕН

  • 🎨 Стилизация/креатив — написание писем, поэзии, генерация идей без фактической базы.
  • 🧮 Математика и логика — модели и так хорошо считают, retrieval не помогает.
  • 📏 Очень короткие ответы — RAG добавляет latency, а польза нулевая.
  • 🔁 Статичные знания — если данные не меняются, дешевле использовать fine‑tune.
  • ⚙️ Высокоскоростные системы (<100мс) — RAG добавляет поиск, что увеличивает latency.

RAG vs fine‑tune: таблица принятия решений

  • Новые знания (частые обновления) → RAG
  • Стабильный корпус документов → fine‑tune (или RAG, зависит от объёма)
  • Нужны ссылки на источники → RAG (обязательно)
  • Требуется изменить стиль ответов модели → fine‑tune
  • Глубокое понимание узкой предметной области → fine‑tune
  • Объём знаний > контекстного окна модели → RAG
«Правило большого пальца: если нужная информация помещается в контекстное окно модели (128K–1M токенов), можно обойтись без RAG. Если нет — RAG необходим».

Гибридные подходы

Часто применяют RAG + fine‑tune одновременно:

  • Fine‑tune обучает модель формату ответа и стилю цитирования.
  • RAG предоставляет актуальные факты.
  • Пример: корпоративный чат‑бот — модель дообучена на тоне компании, а документы загружаются динамически.
# Когда fine‑tune не заменяет RAG: расчёт параметров # Допустим, у нас 1 млн документов по 1000 токенов. # Fine‑tune даже LoRA 7B модели на таком объёме стоит ~10k$ и требует переобучения каждую неделю. # RAG: индексация один раз + дешёвый поиск.
⚠️
Важно: RAG не панацея от галлюцинаций. Если retrieval вернул нерелевантные чанки, LLM может сгенерировать бред. Нужны guardrails и проверка faithfulness.

Кейсы из практики

  • Поддержка клиентов: RAG на базе статей базы знаний → уменьшение эскалаций на 40% (данные из отраслевых отчётов, точные цифры требуют проверки вендоров).
  • Юридические консультации: RAG на законодательстве → обязательны ссылки на статьи.
  • Медицинские Q&A: категорически нужен high‑recall retrieval, ошибки недопустимы.
